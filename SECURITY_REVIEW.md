# Security review — implementation review, not an independent audit

Wallet login now builds explicit EIP-4361 messages with a cryptographically random 128-bit nonce, checked account/chain, domain, URI, issuance and expiry. It requests personal_sign through the connected wagmi wallet, checks the signature locally, and uses native Supabase Web3 authentication. Identity is derived from verified web3 Ethereum identity claims, never editable profile metadata. Session restore checks the server user and rejects mismatches. Real browser-wallet behavior remains unverified.

The additive SQL upgrade enforces membership, borrower-only lender selection, interested-member selection, no self-lending, exact 6-decimal request validation, locked contract terms, and service-only monotonic status transitions. Local three-user tests pass. Client telemetry imports that captured request bodies were disabled. No populated environment or logs belong in release packages.

The verifier authenticates the caller with Supabase's platform JWT gate and `getUser()`, then reads with RLS before service access. It allowlists chain/contract, checks the USDC token, successful creation receipt and borrower, creation event, exact terms and contract state; it scans lifecycle events in bounded batches. The frontend does not authoritatively set funded/repaid status. Version 1 is deployed, but live integration testing is still required. A malicious/compromised service role remains privileged; secure the Supabase account and secrets.

The existing immutable Solidity contract has no admin, interest, collateral or pooled custody. SafeERC20 transfers and nonReentrant funding/repayment follow checks-effects-interactions. Its 31 tests pass. No Solidity source change was needed. Loans are unsecured; nonpayment cannot be forcibly recovered. USDC issuer restrictions can cause transfers to revert. Extremely large durations can overflow when funded; normal UI durations are capped but direct callers are not. This causes a failed loan operation, not custody loss.

The Supabase security adviser reports 11 `SECURITY DEFINER` functions callable by `authenticated`, including the member-facing community RPCs and `prepare_loan_binding`. This is the intentional application API, and each mutation verifies `auth.uid()` and appropriate membership/ownership inside the function; the warning does not constitute a completed audit. Outstanding: independent audit, browser-wallet and cross-device tests, complete backend integration tests, rate-limit/load review, mainnet deployment verification, public-repository history scan, and bundle optimization. EOA wallet signing is covered by the current local signature verifier; smart-contract wallets are not validated as supported. SIWE messages must only be signed on the trusted deployed origin. Onchain financial details are public even when chat is private.
